# 派单列表与长任务详情的信息层级

## 真实问题与变化

协作列表原先将状态、负责人和前 100 字任务内容放在一行按钮中；长任务难以扫读，也看不到已记录的汇报或取消原因。详情又把整段任务作为大标题，长任务会把负责人会话入口挤到首屏之外。原生长任务走查复现了这个问题。

现在列表分开显示状态、负责人、两行任务摘要及已有汇报/取消原因的一行摘要，存在产物时显示数量。摘要按 Unicode 字符取前 320 字再合并空白，不改派单原文或复制内容。按钮保留可访问名称和现有点击/焦点行为。

详情先展示状态、来源、负责人会话和派单编号操作，再展示正常字号的完整任务；新增复制完整任务入口，沿用应用现有剪贴板写入路径。任务、汇报、产物与消息保持原始数据，不将回复结束解释为任务完成。列表状态筛选在窄窗口可换行。

## 原生验证

隔离 Pi 配置、真实 Hive HTTP/SQLite、原生 Pi SDK 会话及真实 team CLI：主控创建一张长任务，写入 8 条核验说明；成员读取真实 required_seen_seq 后显式汇报并关联实际 proof.txt。另创建 24 张任务和一张取消任务，共 26 张。

原生浅色、深色与 760px 窗口验证范围：

- 状态筛选、卡片中的长任务、汇报摘要、取消原因和产物数量。
- 通过卡片点击进入详情，完整任务和汇报逐字保留，包括换行和尾部标记；真实产物路径保留。
- 进入实际负责人成员会话，再返回同一派单；已读取的核验消息保留；返回列表仍为原“已汇报”筛选。
- 26 张派单的真实两页读取，第二页 6 张；分页前先滚动到实际可见按钮再注入鼠标事件。

证据在 `.artifacts/dispatch-cards/`：各外观截图、收据、完整夹具源码和 seed。使用 GPUI 原生事件注入，不是物理键鼠或 Windows GUI 验收。三份最终收据均为零模型请求；夹具另设拒绝执行的本地端点，防止意外发起厂商推理。所有测试模型配置均为 gpt-6.1-terra。

首轮夹具把 report/cancel 的成功空输出当作 JSON，已按原始 CLI 命令输出契约修正；生产代码没有为测试添加 fallback。长任务首次导航超时后，检查渲染截图发现负责人入口位于任务长标题后；已调整真实布局，再验证往返路径。
