# macOS 整包签名更新

打包脚本支持 `--mac-sign IDENTITY`。用 `-` 可以在本地进行临时签名。签名版应用先写入版本、平台、架构及包内文件数，再为整个应用签名。写入的包身份也在签名保护范围内。新格式的文件数不计入签名生成的 `Contents/_CodeSignature`。

更新渠道的 Ed25519 签名保护版本和归档摘要。解包后，后台还会核验 macOS 应用签名与 Hive 的应用标识，并计算签名后主程序的 SHA-256，供本次安装及恢复核对。独立安装程序在替换前再验证主程序摘要和整包签名。该方式遵循 Apple 在资源完成后签名、验证时检查完整包的顺序。[Apple macOS 代码签名说明](https://developer.apple.com/library/archive/technotes/tn2206/)

现有的未整包签名 macOS 开发包及 Windows 包继续使用原格式。支持新格式的后台可以从旧格式过渡到签名包。先前只识别旧格式的安装程序需要先取得支持新格式的后台。采用新格式安装的 macOS 应用会拒绝未整包签名的候选包。

## macOS 原生验证

用打包脚本生成 `0.1.0`、`0.1.1` 两个 arm64 临时签名应用。两次都通过原生设置页检查、下载、安装和重启。渠道仅监听本机回环地址。

| 用例 | 已核验结果 |
| --- | --- |
| 完整签名包正常更新 | `0.1.0` 更新到 `0.1.1`。安装后的应用通过 `codesign --verify --deep --strict`，主程序 SHA-256 与安装计划一致。设置页显示安装成功，原会话和未发送草稿可读。 |
| 签名有效但后台无法启动 | 在有意终止后台启动的测试包上重新进行整包签名。安装程序在启动确认超时后自动恢复 `0.1.0`。旧版主程序前后 SHA-256 一致，应用签名仍有效，设置页显示恢复成功，原会话和未发送草稿可读。 |

两次观察到原窗口正常关闭。验证结束后，新版、恢复出的旧版、它们的后台和独立安装进程均已退出。签名归档分别为 164,861,437 和 164,854,466 字节。证据位于 `.artifacts/macos-signature-update-gWRvqN/` 的 `healthy/receipt.json`、`broken/receipt.json`、两份原窗口日志及打包日志。没有模型调用、正式发布或替换已安装实例。

## 回归检查

更新专项用真实 macOS 签名和本地 ZIP 检查三种损坏或降级情况。有效的渠道签名不能让损坏的应用签名通过。已验证的候选目录在交接后被改写，独立安装程序会在移动旧版前停止并恢复旧版运行。安装在签名应用上时会拒绝旧格式的候选包。旧格式升级到新格式的安装计划通过检查。旧路径的签名下载、离线准备、回退和安装中断恢复测试也通过。

类型检查、Windows MSVC 交叉检查、源码与包内更新专项通过。两个签名应用的包内 Node、PTY、Hive SQLite 工作区及关闭冒烟通过。正式 Developer ID 签名、公证和当前代码的 Windows 原生替换仍待实测。
