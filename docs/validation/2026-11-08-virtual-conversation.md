# 长会话可变高度虚拟列表

## 实际问题

会话累积数百、上千条消息后，Agent 每次更新一条回复，原界面仍构建、布局整个消息区。Mac arm64 的实际 GPUI 开发构建，在 1000 条简单合成消息中，更新最后一条后的单次 CPU 重绘中位数约 194 毫秒。用户继续阅读和操作会受到整个历史长度的影响。

改为 GPUI `ListState` 可变高度列表，实际布局可见区域及少量预渲染区域。已完成工具的分组头和展开后的每项工具分别成为列表行；不是把整个展开工具组塞进一行。不做此项，长历史仍随每次流式更新重复布局。

## 行为保留

- 原正文、Markdown、工具详情、来源原文、成员与派单入口继续复用原渲染方法；消息和尾部视图拆入 `conversation_list/view.rs`。
- 查找先展开目标，再按消息身份定位虚拟行，替换原嵌套 ScrollAnchor 延迟回调。
- 阅读位置保存消息 / 分组身份与行内偏移，消息前方变化或分组折叠后重新映射。调用现有会话位置保存 / 恢复函数检查通过。
- 正在跟随末尾时保持跟随；用户上滚或查找时暂停，回到最新恢复跟随。
- 只重新测量发生变化的行。Markdown 异步解析完成后通知外层列表，避免沿用旧行高；选择和淡入通知不额外触发这项失效。
- 待处理汇报和原生提问留在同一滚动区域；尾部表单及 Markdown 行注册焦点，使有焦点的内容滚出视口后仍保持键盘交互。
- 未测量行使用高度估计，滚动条尺寸随实际布局收敛。窗口宽度变化后恢复估计，避免列表丢弃未测量行的高度提示；不会为了滚动条初始尺寸先测量整个历史。

## 同条件测量

基线 `1fa983a`。同一 Mac arm64、760×620 窗口、未优化开发构建；相同合成内容，先运行四帧，再更新最后一条普通文本消息并采样 12 次。计时只包括显式 GPUI CPU 布局 / 场景生成，不包括 GPU 呈现、模型、网络或端到端输入延迟。

| 消息数 | 修改前中位数 | 修改后中位数 |
| --- | --- | --- |
| 180 | 34.57 ms | 2.46 ms |
| 1000 | 194.03 ms | 2.61 ms |

原始日志：`.artifacts/chat-performance/before-last-{180,1000}.log` 和 `after-final-{180,1000}.log`，完整样本与边界在 `result.json`。较早的 `before-*` / `after-last-*` 试跑日志也保留，但上述表格只用同一“修改最后一条”工作负载。

这些数字证明该合成场景下重绘成本明显下降，不代表正式优化构建、真实大表格 / 图片、内存占用或所有后端会话已经达到性能目标。

## 实际原生检查

临时应用源码副本使用真实 Node / HTTP / SQLite 工作区及会话记录，消息、工具结果和提问是合成数据，没有模型请求。锁屏时使用此前的测试专用 GPUI 帧驱动，按原框架顺序执行回调、布局与场景渲染；生产应用不包含该驱动或修改后的框架。

通过：

1. 中文 / 英文大小写查找、无匹配、工具参数与汇报原文、前后循环及流式匹配更新。
2. 真实布局定位早期消息和折叠组内工具；浅色窄窗截图检查了横向边距与工具详情。
3. 真正 `AssistantDelta` 更新没有拉走阅读位置。
4. 屏幕外 Markdown 异步解析触发额外布局失效；随后定位该消息，实际测得超过 500px 的行高。
5. 行内 150px 阅读偏移经前方消息增长、实际会话位置保存 / 恢复函数后保持，工具展开状态一并恢复。
6. 待回应 Pi 输入框滚出视口后保留原生焦点，派发 Backspace 编辑 Action，实际中文草稿由“回答草稿”变为“回答草”；没有提交回答或启动 Agent。
7. 1000 项展开工具各自注册行，早期屏幕外工具保持未测量；中间第 500 项可定位，折叠后映射到对应分组头。

成功标记与过程日志在 `.artifacts/chat-performance/functional-source-final.log`；图片在 `.artifacts/virtual-conversation/`。

一次分组夹具错误要求末尾分组折叠后仍保持在视口顶部，实际列表在剩余内容不足时自然贴底，断言失败。保留末尾贴底行为，改用分组后仍有内容的场景验证身份锚点，没有添加生产兜底或更改产品语义。较早的 `functional.log` 保留该失败。
