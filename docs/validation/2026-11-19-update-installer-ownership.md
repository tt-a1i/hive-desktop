# 桌面更新的取消、清理和重试

本文末尾记录的旧身份格式与整包签名冲突已在[后续 macOS 整包签名更新](2026-11-19-macos-signed-update.md)中修复并用本地临时签名验证。

普通退出、安装前草稿保存失败、安装准备完成时检测到新任务这几条路径均会释放尚未启动的安装程序和恢复入口。可重用的已校验归档保留。后台只向收到确认的安装交接保留该次准备结果。桌面收到同一安装的确认并核对后台进程范围已退出后，才启动独立安装程序。

## macOS 原生验证

在隔离的 `0.1.0` 开发包中，通过设置页检查并下载回环渠道签名的 `0.1.1` 归档。文件共 163,032,775 字节，由 Ed25519 签名清单提供 SHA-256。沿用此前验证过的 `0.1.1` 更新归档，这次重建了负责准备和启动安装的旧版桌面及其包内后台。

1. 原生输入框保留新编辑的草稿，临时用隔离数据目录下的测试文件阻止草稿写入。安装准备成功后，窗口提示草稿保存失败。原应用二进制的 SHA-256、持久化草稿和新编辑内容均核对通过。
2. 生产 JSONL 回执确认安装准备及取消。安装目录和恢复入口消失，未出现安装结果，旧程序继续运行。重新计算缓存归档的大小和 SHA-256，结果与签名清单一致。
3. 恢复草稿目录，在设置中重新确认安装。运行期间只下载一次。包内后台确认安装交接，旧程序和后台退出。安装收据记录 `0.1.1` 已安装。新版真实窗口重新打开原会话并显示新编辑的草稿，设置页显示安装成功。关闭窗口后核对两版桌面、后台和安装进程均已退出。

真实包证据位于 `.artifacts/update-installer-ownership-mac-Vks4Xa/` 的 `receipt.json`、`discard-receipt.json`、`desktop.log` 及安装收据。该流程未调用模型，未替换已安装实例或公开发布。

当前开发包由更新渠道签名清单保护归档，macOS 二进制为链接器临时签名。本地另对整个隔离 `.app` 作临时签名，发现签名会改变可执行文件摘要，而重新写入摘要又会改变签名输入。当前包身份文件和整包签名还未形成可部署的组合。该预检拒绝了二进制与身份不匹配的副本，证据保存在 `.artifacts/update-installer-ownership-mac-chg1wg/desktop.log`。正式签名和公证仍待推进。

## 低磁盘空间准备和首次记录前的恢复

`fc3d37b` 让 macOS 在同卷准备更新时优先使用写时复制。已下载归档的副本仍要核对文件大小、SHA-256 和签名。临时安装器继续使用独立的 Node 文件，旧应用被替换后仍可运行。跨卷使用系统复制，Windows 继续走原文件复制。当前包内 Node 的克隆标志在实际 APFS 上返回 `ENOSYS` 或退回普通复制。选择 macOS 自带的 `cp -c`，同卷克隆和跨卷回退都经过实测。下载或准备阶段真实返回 `ENOSPC` 时，设置页会提示释放空间并重试。[Node 22 文件复制选项](https://nodejs.org/download/release/latest-jod/docs/api/fs.html#fspromisescopyfilesrc-dest-mode) · [macOS 系统复制实现](https://github.com/apple-oss-distributions/file_cmds/blob/main/cp/utils.c)
