# 长 Codex 历史搜索与普通 ACP 冷队列

## 历史搜索

Codex 历史搜索在单次查询中为投递记录建立查找表，按原顺序优先匹配继承的精确记录，随后匹配本地精确记录及旧格式用户投递。原始投递 ID 用于跳到消息。查找表只在当前查询内使用，历史改写后下次搜索重新读取文件。

两次比较均从解包后的 macOS 应用运行，使用同一个 Node 22.23.3 和同一份合成 Codex 历史。每种规模预热一次，取七次的中位数。每次都完整定位末尾消息及对应原始投递 ID。

| 历史回合 | 原版 | 修复后 |
| ---: | ---: | ---: |
| 2,000 | 81 ms | 15 ms |
| 4,000 | 261 ms | 29 ms |
| 8,000 | 981 ms | 56 ms |

生产 JSONL 探针在 16,000 条历史项的 JSON 解析结束时发出取消。原版遍历到了最后一条并返回完整结果，随后拒绝取消。新版在遍历到最后一条前处理取消，约 26 ms 后原请求返回 `SEARCH_CANCELLED`。紧接着再搜仍命中 `delivery-7999`。原生窗口也从另一个项目的会话进入全局搜索，打开结果并定位到历史末尾的目标消息。

## 普通 ACP 冷队列

GPT-6.2 Sol 独立对照总目标，复现了普通 ACP 会话必须激活才能通过界面修改待发队列的缺口，并补齐本地写入。适用范围为原成员仍绑定、固定后端配置有效、保存的原生身份吻合且已确认支持恢复和 Hive 协作的会话。

在原生窗口打开冷会话，编辑带附件消息并撤回另一条，退出再开后两项操作仍有效。持久化队列保留投递 ID 和附件上传 ID。受控 ACP 对端的协议日志在打开、编辑、撤回和冷重开期间完全一致。点击继续后，同一个原生会话收到一次编辑后的正文和原附件引用，未收到撤回内容。专项回归另外覆盖 SQLite 源记录调和、过期编辑、错误原生身份、原成员解除绑定和 `started`、`sent`、`completed` 保护。

## ACP 接续完成后的冷队列

GPT-6.2 Sol 复现了旧版在冷打开 ACP 接续目标时锁住后续待发消息的问题，也复现了冷态放弃不确定投递后缺失队列更新。`312f5d0` 允许离线编辑和撤回已确认尚未开始投递的消息。会话需保留原成员和固定后端配置，接续回执须与保存的 ACP 原生会话对应，原生记录也须确认首条接续消息已经完成。其他后端尚未验证相同的冷态编辑条件。

在 macOS 解包应用的原生窗口编辑带附件的待发消息并撤回另一条。退出重开后，修改、原投递 ID 和原附件上传 ID 均保留。打开、修改、撤回和重开期间，受控 ACP 对端日志的字节完全一致。点击「继续处理」后，原会话收到一次编辑后的正文和附件引用。撤回的消息没有送出，历史接续上下文也没有重复投递。源码探针另外验证了 SQLite 事务回滚后的文本恢复和已提交撤回记录的调和。

在另一个冷 ACP 会话的原生窗口审查并放弃不确定投递。当前窗口立即撤下原消息重试入口。队列清空，ACP 记录仍保留 `sent`，窗口无需重新打开会话，对端协议日志保持原样。专项回归验证相同请求可安全重试，以及持久化失败时保留待发项。

本轮 macOS ZIP 经本地签名和解包校验，三个原生窗口均正常退出，记录的所有子进程均已退出。便携包冒烟、包内接续和 ACP 的三项专项、129 个 Rust 测试及 Windows 目标编译检查通过。本轮原生流程使用受控 ACP 对端。Windows 原生窗口与实际模型另行验收。
