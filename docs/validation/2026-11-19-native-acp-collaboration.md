# macOS 原生 Codex 与官方 ACP 协作

修复了 ACP 成员启动按钮误要求桌面模型的缺陷。ACP 由适配器管理模型。修复前使用有效的 ACP 配置打开成员页时，启动按钮不可用。修复后同一入口可启动成员并显示待命。

macOS arm64 本地优化包的源码为 `1b3c069ac174e5ec6f30a52a4947beeeebd44706`。从已有的优化包复用生产运行时、Node 和资源，只替换由该提交编译的桌面程序，再重新签名和打包。窗口运行了重新签名的应用目录。ZIP 解包后逐项核对 28,956 个文件、29 个链接和 2,709 个目录，并验证严格签名。ZIP SHA-256 为 `a10d867622a8047b8085cc843212e4c3541ecb53bd8f4ff8ba78057b93e31899`。

## 真实原生流程

准备阶段用生产运行时创建隔离仓库、两个会话及各自的工作树和固定启动配置，并提前写入 ACP 成员会话的绑定。正式运行从原生成员页启动 ACP，再回到原生 Codex 会话输入并提交一次测试消息。ACP 使用官方适配器 `@agentclientprotocol/codex-acp@2.6.0`，原生 Codex CLI 为 `0.169.0`。传输边界核对两端模型均为 `openai/gpt-6.1-terra`，使用同一已有账号。

1. 主控发出一个派单。ACP 成员在自己的工作树读取种子文件，生成测试文件并核对实际字节的 SHA-256。它通过真实 Hive 工具读取派单的消息序号，再提交一次带文件的汇报。
2. 汇报自动回到原主控会话。主控在收到汇报后执行文件读取和 SHA-256 校验，窗口显示校验通过。独立检查器核对 SQLite 中的一条派单和一条成功投递的汇报、两端原生身份、固定配置、工作树和真实工具结果。实际推理为三次开始和一次续写，其中 ACP 开始一次。
3. 退出并重新打开应用。窗口重现主控结论、成员汇报与文件入口，点击汇报中的原成员会话可打开保存的 ACP 对话。冷启动和被动查看都没有推理，也没有重新启动 ACP。两次正常退出后，观察到的桌面、后台及子进程均已回收。

Rust 120 项测试通过，1 项子进程入口按设计忽略。实际包内 Node、PTY、HTTP 与 SQLite 工作区、退出冒烟均通过。Windows x86_64 MSVC 交叉检查通过，当前流程仍待 Windows 原生验收。
