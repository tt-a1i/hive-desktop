# 普通文件附件与发送正文保真

日期：2026-11-08。完整桌面产品仍在实施。

## 真实问题三问

1. 用户把需求文档、代码或 PDF 交给当前 Agent 时，桌面只允许添加图片，普通文件会被拒绝；还必须在原始文件移动后保留可读取的附件。原生走查另发现聊天 Enter 会在提交前插入换行，改变实际正文。
2. 现在可选择、粘贴文件路径或拖入普通文件，与图片混合发送；草稿和历史显示名称、大小，原文件删除后仍保留 Hive 上传副本。当前 Agent 收到副本的本机路径，通过自己的工具按需读取。Enter 发送保持正文，Shift+Enter 保留换行能力。
3. 不做则用户需要手工复制路径/正文，丢失附件关联，文件移动后无法重读；而 Enter 改动正文会影响精确指令和代码片段。

## 实现与数据边界

- 复用 Hive 2.2.1 原有 workspace_uploads 表、上传 HTTP、工作区删除及 user_input/outbox；没有新增附件 store、表，也没有修改 Hive 业务协议。每条最多 10 个附件，普通文件沿用 Hive 的 100 MiB 单文件限制；原生图片仍沿用原有格式、单张及合计限制。
- 对固定 Hive 补丁只增加内部 `locateWorkspaceUpload` / `locateUpload`：复用原 prepared query、工作区作用域及 storage_key 安全路径解析，返回记录和本机路径，检查磁盘文件存在。普通文件恢复/定位只读元数据和 stat，图片需要预览时再读字节。原 readUpload 和公开 HTTP 返回保持原样；本机路径没有进入 HTTP 上传列表。
- `chat.attachments.add/get` 现支持混合附件，图片返回原 image 块，普通文件返回 filePath 与附件记录；`chat.attachments.path {workspaceId,id}` 重新验证归属/存在后返回副本路径，供本机文件管理器定位。ID 仍有严格 UUID、数量及重复校验；不接受客户端传来的任意存储路径。
- 用户消息仍按已有带版本 ID 标记恢复。历史编码函数与 `hive-desktop-images:v1` 标记保留原样，里面一直是上传 ID 列表；旧图片和用户粘贴的字面标记转义没有改格式。
- 交给模型的是明确区分用户数据的文件路径清单；文件内容不自动内联，不提取 PDF、不运行附件、不自动授予原生 Agent 权限。图片继续进入四种适配器原生图片输入。上传副本隔离原文件的修改/删除，但不承诺防止用户或 Agent 手动改写副本。
- 队列沿用当前持久化：图片字节照旧保存，普通文件引用已有 Hive 上传副本；显式用户展示保留原正文、附件名称/大小和来源。无正文的文件消息也可发送，标题为“附件消息”。
- 桌面复用原文件选择器、ExternalPaths 粘贴与拖放入口、草稿保存和恢复。文件卡片显示名称/大小，可移除；历史和草稿都可请求本机定位副本。长标签约束在可用宽度内并省略，完整名称在提示和辅助标签中保留。
- 对聊天 TextareaState 启用现有 submit_on_enter：共享入口修复所有聊天的 Enter 插入换行问题，没有 trim 或重写用户正文；其他多行配置字段不变。

## 证据

本地收据、截图和执行源位于 `.artifacts/file-attachments/`。

### 真实厂商推理与桌面恢复

`file-attachments-native-codex.ts` 显式使用原始 Codex 0.166.0 和 openai/gpt-6.1-terra，无模型回退。上传自有测试文本后删除原始文件，只向模型说明读取附件，未把文件里的随机校验值放入提示词。真实原生工具执行 cat 读取 Hive 副本，最终返回附件内的校验值，副本字节保持。收据为 native-codex-receipt.json。

只读重开随后核对：原生工具输入指向上传路径，工具输出与文件内容匹配，历史保留附件身份。该同一原生会话已在真实 GPUI 中打开，文件卡片、工具过程和最终回答显示正确；此次 GUI 读取没有再发 prompt。见 native-codex-readback.json、real-codex-ui.png 和相应日志。这证明 Codex 原生通道本轮可用，不代表先前失败的 Pi OAuth 已修复。

### 真实本地链路与合成对端

- `check:files`：真实 Hive HTTP/SQLite/上传、内置 Pi SDK、原始外部 Pi RPC，以及生产 JSONL；模型统一声明 gpt-6.1-terra，调用只到本机拒绝端点，没有厂商推理。覆盖源文件删除后的副本保真、队列/原生历史重开、纯文本模型传文件、零字节和文件单独发送、图片能力拒绝、缺失/跨工作区/非法 ID、目录/相对路径、100 MiB 以上的稀疏文件、伪造图片头及内部路径不进入公开 HTTP 列表。
- `check:files-claude-peer`：官方 Claude SDK + 明确合成 CLI，验证文件路径进入真实 SDK 输入流而非文件正文、取消和恢复后附件元数据；合成模型元数据为 Terra。这不是原始 Claude 的模型或工具读取验收。
- 原图片附件 HTTP/JSONL 回归、团队投递、Codex 传输/恢复/交互、Claude SDK 交互回归保留并运行；共享 Claude 合成 peer 仅扩充测试 query 记录，用于检查自己生成的附件输入，没有修改生产 Claude 协议。

### 原生界面

浅色、深色与 760px 窄窗各跨三次实际应用进程，原生布局及注入鼠标/KeyDown/FileDrop 事件验证：

- 文件路径粘贴回调与图片拖放、普通文件移除/重加、混合卡片和中文草稿保存；源文件在上传后删除。
- 重启后暂时移走上传副本，发送就绪状态被阻止，正文和附件保留，没有请求到模型；恢复文件、点击重新读取后可继续。
- Shift+Enter 产生用户要求的换行，重置为指定正文后 Enter 发送，历史和重开后的正文逐字一致；没有额外前导换行。
- 各自只出现一次预期的本机拒绝请求，三次启动后的历史仍有文件和原生图片；打开历史不自动调用模型。

首次检查发现 Enter 的生产输入模式错误；启用原生提交模式后，继承的 dispatch_keystroke 测试 helper 又会补发模拟 IME 的换行，因此改用原生 KeyDown 事件核验。没有为了测试给消息加 trim 或特殊分支。最初的失败日志保留，最终以三种窗口和真实正文断言为准。

上述不是系统物理拖拽/粘贴/键盘验收，系统文件选择器与 Finder/Explorer 定位尚未实际点击验收。通用文件展示是元数据和定位入口，没有内置文档内容预览；具体文件解码仍取决于当前 Agent 的工具。
